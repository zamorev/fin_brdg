# Экраны родителя — адаптация спецификации под репозиторий

**Статус:** черновик на обсуждение (2026-11-01). Код не менялся.

Источники:

- макет: Claude Design «Fin Bridge — родитель» (4 артборда: главная, запросы, договорённости с подростком, шторка категории);
- спека: Claude Docs «Fin Bridge — спецификация экранов родителя».

Документ сверяет их с тем, что сейчас лежит в `functions/` и `v2/web/`, и перечисляет решения, без которых экраны не собрать.

## 1. Короткий вывод

Макет и спека описывают **договорённость на каждого подростка**: свой недельный бюджет, свой набор категорий, свои правила, свои запросы. В репозитории всё это хранится **одно на семью**:

| Что | Спека | Сейчас в коде |
|-----|-------|---------------|
| Разбивка по категориям | у каждого подростка своя | `families.allocation` — одна на семью (`store.ts:52`) |
| Недельный бюджет | у каждого свой, родитель меняет | `families.teenWeeklyBudgets[teenId]` есть, но только заполняется дефолтом 1 500 (`syncTeenWeeklyBudgets`); API на изменение нет |
| Уровень, навыки, квесты | у каждого свои | `level`, `skills`, `quest*Completed` — на семью |
| Запрос | от конкретного подростка, по любой категории | у `RequestDoc` **нет `teenId`**, `category: "entertainment"` захардкожен |
| Ожидающие запросы | список по семье, счётчики | `getActiveRequest` берёт **один последний** запрос семьи |
| Категории | динамические: создать, удалить, `allowRequests`, цвет | фиксированный enum из 5 ключей + минимумы из квеста 1 |

Связь подросток ↔ родитель сейчас есть, но узкая: один общий бюджет семьи, один активный запрос «развлечения 400 → N», решение родителя `approve_week / reject / needs_clarification` переписывает `allocation.entertainment`. Подросток видит статус через `/api/me`. Уведомлений в бот о решении нет. Кто именно из подростков спросил — неизвестно.

С двумя и более подростками текущая модель ломается уже сейчас: квест одного подростка перезаписывает разбивку другого. Макет (4 подростка) без смены модели данных не реализуем.

## 2. Противоречия

### П1. Кто распределяет бюджет по категориям

- **PRODUCT.md / квест 1:** подросток сам раскладывает 1 500 ₽; родитель задаёт рамки (минимумы на обязательное, накопления, резерв), «остаток можно распределять самостоятельно». На этом стоит продуктовая гипотеза про делегирование.
- **Спека/макет:** родитель сам ставит лимит каждой категории степпером. Подросток только просит изменить одну.

Если оставить спеку как есть, квест 1 теряет смысл (что подросток распределяет, если лимиты задал родитель?), а продукт сдвигается от «учимся решать» к «родитель контролирует».

### П2. Набор категорий и минимумы

- Код: `transport / food / entertainment / savings / reserve`, минимумы 300 / 500 / — / 200 / 100, валидация «сумма ровно = бюджету».
- Макет: «Еда и перекусы», «Транспорт», «Развлечения», **«Подписки»** (нового нет в коде), «Резерв»; **«Накоплений» нет**. Шаблон для нового подростка — с нулевыми лимитами, что нарушает минимумы.
- Спека разрешает перебор (`allocated > weeklyBudget`) и сохраняет его; домен считает это ошибкой.

### П3. Правила родителя

- PRODUCT.md: правила — это минимумы (обязательные ≥ 800, накопления ≥ 200, резерв ≥ 100).
- Спека: «Запросы на изменения», «Срочные покупки > 500 ₽ — сначала спросить меня», «Остаток копится».

«Срочные покупки» и «остаток копится» предполагают учёт реальных трат, начисление по понедельникам и часовой пояс семьи. Трат в продукте нет (суммы условные, банк и карты вне MVP), недели и начисления тоже нет. Это та же дыра, что в T22 («правила ≠ остаток»).

### П4. Жизненный цикл запроса

| | Код (`RequestStatus`) | Спека |
|-|------|-------|
| Статусы | `pending`, `approved`, `rejected`, `needs_clarification` | `pending`, `needs_info`, `approved`, `declined`, `countered` |
| «Попросить уточнить» | финальный статус, подросток ответить не может (X3 из T22) | запрос остаётся открытым, после ответа возвращается в `pending` |
| Своя сумма | нет | `counter { limit, fundingSource }` |
| Откуда деньги | не учитывается | `fundingSource`: резерв или рост бюджета |
| Потолок суммы | `proposed ≤ 1 500` (`validateRuleChange`) | лимит до 100 000 |
| Гонка двух родителей | `throw "Уже ответили"` → 400 | 409 + «Уже решено: {статус} ({Имя родителя})» — нужно поле `decidedBy` |

`counter` в спеке — **финальный** статус: родитель предложил сумму и запрос ушёл в «Недавно решено». Подросток согласия не даёт. Нужно решить, нормально ли это (см. Р5).

### П5. Родитель на главной не видит квесты и навыки

DoD п. 4 и задача T20 требуют, чтобы родитель видел результаты квестов и навыки. В макете их нет ни на главной, ни в экране подростка: там только шапка «3 уровень · 12 заданий за месяц». Поля `tasksThisMonth` в данных нет, `level` — константа семьи.

### П6. T20 в бэклоге описывает другой дашборд

В T20 главная родителя — это блоки «Договорённости / Квесты / Навыки / Запрос» из `family.allocation`, без нового API. Новый макет задачу заменяет, и без изменений бэкенда (K2) его не сделать. T20 и T22 надо переписать, а не делать по старому тексту.

### П7. Тема

Макет захардкожен: чёрный фон в стиле iOS (`#000`, `#1C1C1E`, …). Приложение берёт цвета из темы Telegram (`--tg-theme-*` → `--fb-*` в `global.css`) и работает в светлой теме. При светлой теме Telegram чёрный экран родителя будет выбиваться.

### П8. Бот

Спека шлёт подростку сообщение на каждое решение и правку, склеивая правки за 2 минуты. В коде бот шлёт только шаг сценария (`scenarioNotify.ts`). В PRODUCT.md «расширенный бот (рассылки…)» помечен как вне MVP. Уведомления о решениях по запросу туда вряд ли входят, но границу стоит зафиксировать.

### П9. Мелочи, где спека не знает репозиторий

- Стор Zustand/Redux: во фронте нет зависимостей кроме React; сессия целиком приходит из `/api/me`, после мутаций сервер возвращает новую сессию.
- Пути `/family`, `/agreements/…` → у нас `/api/…`; решение сейчас одно на `POST /api/requests/:id/decide { action }`.
- Удаления подростка из семьи в продукте нет, поэтому «авто-decline при удалении» пока не к чему привязать.
- Подсказка «Нажми на подростка…» хранит флаг в Telegram CloudStorage; сейчас CloudStorage нигде не используется (это нормально, просто новое).

## 3. Решения, которые нужно принять

Рекомендация дана к каждому пункту. Её можно оспорить.

| # | Вопрос | Варианты | Рекомендация |
|---|--------|----------|--------------|
| Р1 | Договорённость — на семью или на подростка? | на семью / на подростка | **На подростка.** Новый документ `families/{familyId}/agreements/{teenId}` или коллекция `agreements` с ключом `teenId`. Уровень, навыки и квесты тоже переезжают к подростку. Без этого макет не работает. |
| Р2 | Кто раскладывает бюджет по категориям (П1) | родитель задаёт лимиты / подросток раскладывает в рамках | **Гибрид:** родитель задаёт недельный бюджет, состав категорий и **минимум** (или «фиксировано») для каждой; подросток раскладывает остаток в квесте 1. Тогда степпер в шторке — это минимум/лимит, квест 1 сохраняет смысл. Если нужен быстрый результат — делать по спеке, но записать в core-beliefs, что делегирование откладывается. |
| Р3 | Категории (П2) | фиксированные 5 / шаблон + свои | Шаблон по макету + «Накопления», свои категории позже. **Резерв обязателен и не удаляется** (как в спеке). Минимумы из `domain.ts` превратить в дефолты шаблона, а не в жёсткие правила. |
| Р4 | Правила (П3) | спека целиком / только то, что считается без трат | В первой версии **только «Запросы на изменения»**. «Срочные покупки» и «Остаток копится» требуют учёта трат и недели — делать после модели T22. В UI либо не показывать, либо показывать неактивными с подписью «скоро». |
| Р5 | Статусы запроса (П4) | оставить старые / перейти на спеку | **Перейти на спеку:** `pending → needs_info → pending`, финалы `approved / declined / countered`. | Р6 | Перебор и нераспределённое | запрещать / разрешать с предупреждением | Разрешать, как в спеке; ошибкой считать только в квесте подростка. |

| Р8 | Уведомления (П8) | все события / только решения по запросу | Только решения по запросу (approve / decline / counter / ask). Правки договорённости родителем — без бота, подросток увидит на главной. Тексты — через CMS (`getMessage`), как у сценариев. |
| Р9 | Квесты и навыки у родителя (П5) | убрать / добавить в экран подростка | Добавить в экран 3 секцию «Квесты и навыки» под правилами. Тогда DoD п. 4 закрыт. Шапку «N заданий за месяц» заменить на то, что реально считается (пройдено квестов / навыков). |

## 4. Чего не хватает в проекте

### Данные (Firestore, `functions/src/store.ts`, `docs/generated/firestore-schema.md`)

- `Agreement` на подростка: `weeklyBudget`, `categories[] { id, name, kind: 'regular'|'reserve', limit, allowRequests, color, order }`, `rules { requestsEnabled, … }`, `configured`, `updatedAt`, `updatedBy`.
- Прогресс на подростка: `level`, `skills`, статусы квестов (сейчас на семье).
- `RequestDoc` v2: `teenTelegramId`, `categoryId`, `fromLimit`, `toLimit`, `reason`, `status`, `finalLimit`, `fundingSource`, `infoQuestion`, `infoAnswer`, `parentComment`, `decidedBy`, `decidedAt`, `createdAt`.
- Индексы Firestore: `requests` по `(familyId, status, createdAt)` и `(familyId, teenTelegramId, status)`.
- Миграция: текущая `families.allocation` → договорённость каждого подростка семьи; старые запросы → `teenTelegramId` неизвестен (по семье с одним подростком подставить его, иначе оставить в истории без привязки).

### API (`functions/src/app.ts`)

| Метод | Путь | Зачем |
|-------|------|-------|
| GET | `/api/family` | расширить: на каждого подростка `weeklyBudget`, `pendingCount`, `configured`, `allocated` (сейчас только участники) |
| GET | `/api/agreements/:teenId` | договорённость; подросток — только свою |
| PATCH | `/api/agreements/:teenId` | `weeklyBudget`, `rules` (только parent) |
| POST / PATCH / DELETE | `/api/agreements/:teenId/categories[/:id]` | категории; удаление переносит лимит в резерв |
| GET | `/api/requests?status=…` | список по семье вместо одного `activeRequest` |
| POST | `/api/requests/:id/{approve,decline,counter,ask}` | вместо `decide { action }`; 409 при гонке |
| POST | `/api/requests/:id/answer` | ответ подростка на «Расскажи ещё» (нового в спеке нет, но без него `needs_info` тупик) |
| POST | `/api/requests` | расширить: `categoryId`, проверка `requestsEnabled` и `allowRequests` |

Все мутации возвращают обновлённую договорённость и запрос, как в спеке; сессию `/api/me` можно оставить для подростка.

### Домен (`functions/src/domain.ts` + копия `v2/web/src/domain/budget.ts`)

- `allocated`, `unallocated`, расчёт последствий запроса по резерву (4 ветки из спеки), середина для `counter` с округлением до 50, склонения «категория / подросток / задание».
- `validateRuleChange` без потолка 1 500; `validateAllocation` — минимумы из договорённости, а не константы.
- Тесты в `domain.test.ts` на все ветки последствий и `fundingSource`.

### Фронт (`v2/web`)

- Экраны: `ParentHome`, `ParentRequests`, `TeenAgreement` (экран 3), `CategorySheet` (нижняя шторка, 3 режима). Сейчас родитель — это кусок `App.tsx` + `ParentRequest.tsx`.
- Общие компоненты: аватар с цветом по `teenId` (`MemberAvatar` есть, нужен детерминированный цвет), строка списка, сегмент-контрол, iOS-переключатель, степпер с автоповтором, полоса распределения, нижняя шторка, тост, скелетоны.
- Состояние: общий стор для главной и экранов 2–3 (React context + reducer достаточно, без новых зависимостей), оптимистичные обновления с откатом, перезапрос на `visibilitychange`.
- Haptic (`HapticFeedback`) — проверить, есть ли обёртка в `twa/`.
- Сторона подростка: выбор категории в запросе, экран «Мои договорённости» с данными агрегата, ответ на «Расскажи ещё», статусы `needs_info` / `countered`.

### Бот

- `requestNotify.ts` по образцу `scenarioNotify.ts`: 4 события, тексты в CMS-каталоге.

## 7. Что осталось и что появилось

### Новые противоречия

**Н1. Сам запрос из DoD теряет смысл.** DoD п. 3 и текущий код: «Развлечения 400 → 500». У Развлечений минимума нет, и при D2 подросток сам решает, сколько туда положить. Поднять 400 → 500 он может без родителя, перекинув 100 ₽ из свободной части. Запрос имеет смысл, только если он просит то, что подросток сам поменять не может:

- (а) **увеличить недельный бюджет** (+100 ₽, «на развлечения» — как пояснение);
- (б) **снизить минимум** обязательной категории (освободить деньги).

Рекомендация: запрос в MVP = «увеличить недельный бюджет на N ₽» с целевой категорией в пояснении. Тот же тип запроса нужен для срочной покупки (D4), так что это один механизм, а не два. Тексты DoD п. 3 и квеста переформулировать.

**Н2. Разовая добавка или постоянное увеличение.** Срочная покупка (D4) — это разовые деньги на одну неделю, а запрос из DoD — постоянное изменение бюджета. В запросе нужно поле `kind: 'one_time' | 'permanent'` или два разных типа.

**Н3. Срочная покупка требует остатка.** «Не хватает резерва и гибких категорий» можно посчитать, только если хранится, сколько уже потрачено. Это ровно T22 (правила ≠ остаток). Без T22 фаза B механизм D4 не собрать.

**Н4. Запрос на новую категорию (D3) не всегда нужен.** Если подросток выделяет деньги под новую категорию из своей свободной части, разрешение родителя не требуется — это его решение. Запрос к родителю нужен, только когда новая категория требует денег сверх бюджета или нового минимума. Иначе продукт вернёт контроль родителю там, где делегирование уже произошло. Решать при проектировании D3.

**Н5. Отступление от DoD п. 4.** D5 убирает квесты и навыки у родителя, а DoD и T24 их требуют. Либо поправить DoD (явно, в PRODUCT.md), либо оставить минимальную строку. Дёшево: «N квестов» можно считать честно уже сейчас (`questWeekBudgetCompleted` + `questUnplannedCompleted` + завершённые `scenarioRuns`) — хотя бы для семьи с одним подростком.

| Р8 | Уведомления в бот | Только решения по запросу. |
| В1 | Может ли родитель сейчас менять недельный бюджет подростка (степпер на экране 3)? | Да: это и есть ответ на запрос «увеличить бюджет». Нужен `PATCH` для `teenWeeklyBudgets`. |
| В2 | Может ли родитель сам менять минимумы? | Пока нет (D2: заданы с самого начала). Тогда шторка правки категории родителю не нужна. |

### Бот

Шлёт только одно: подростку, когда следующий шаг сценария стал доступен (`notifyScenarioStepReady`). На старт сценария, создание запроса и решение родителя сообщений нет. Родителю бот не пишет ничего.

### «Данные общие на семью» — на примере

Семья: родитель, Аня (бюджет 1 500), Петя (бюджет 2 000).

1. Аня проходит квест 1 и раскладывает 1 500 ₽ → пишется в `families.allocation`.
2. Петя открывает главную: у него «Квест пройден» и Анина разбивка; «Мои договорённости» показывают её цифры. Его квест валидируется по 2 000 ₽, но пишет в ту же `allocation` и затирает Анину.
3. Сценарий «Ой, кино» у Пети списывает −250 из развлечений — у Ани тоже стало меньше.
4. Аня просит 400 → 500, родитель одобряет → Петины развлечения тоже 500. Запрос не знает, чей он.
5. Уровень, XP, навыки — одни на двоих.

Отдельно на подростка хранится только недельный бюджет (`teenWeeklyBudgets`) и прохождения сценариев (`scenarioRuns.teenTelegramId`).

## 11. Объём для видео на хакатон (2026-11-01)

**Цель:** не трогать сценарий подростка; показать у родителя: (1) запросы приходят, (2) каждого подростка можно открыть — бюджет и категории, (3) сумма категории меняется и родителем напрямую, и по запросу подростка.

### Нерешённые проблемы и минимальный выход

| # | Проблема | Почему мешает | Минимальный выход на сегодня |
|---|----------|---------------|------------------------------|
| Д1 | `allocation` общая на семью | при двух подростках оба покажут одни категории, правка родителя изменит обоих | в видео семья с **одним** подростком (или второй без открытия экрана) |
| Д2 | У родителя нет API для правки категорий и бюджета | сейчас `allocation` пишет только квест подростка | новый `PATCH` (только parent): `allocation` + `weeklyBudget` подростка, проверка минимумов. **Нужен деплой Functions** |
| Д3 | Одобрение ломает сумму | `approve` ставит развлечения 500, остальное не трогает → категорий 1 600 при бюджете 1 500 (T22) | при одобрении поднимать недельный бюджет на разницу (как в спеке: «Резерва нет — бюджет станет 1 600 ₽») — правка в `decideRequest` |
| Д4 | В запросе нет подростка | `RequestDoc` без `teenTelegramId`; Д3 не знает, чей бюджет поднять | писать `teenTelegramId` в `createRequest` (1 строка); старым запросам — единственный подросток семьи |
| Д5 | Квест 2 списывает деньги до запроса | после «из развлечений / накоплений / резерва» −250 сумма категорий ≠ бюджету, у родителя полоса покажет «не распределено 250» | в видео выбрать «Отказаться от покупки» — разбивка остаётся целой |
| Д6 | Запрос виден только один | `getActiveRequest` — последний запрос семьи; «Недавно решено» и счётчик по нескольким запросам нечем заполнить | экран запросов: одна карточка + после решения она же в «Недавно решено»; «История» — заглушка |
| Д7 | «Расскажи ещё» — тупик | `needs_clarification` финальный, подросток ответить не может | в видео не нажимать; кнопку оставить, но без отдельной шторки |
| Д8 | «Своя сумма» по запросу | в API нет `counter` | для видео не показывать или сделать как «одобрить с другой суммой» (тот же `decide` + `amount`) |
| Д9 | Нет обновления без перезапуска | родитель увидит новый запрос только после перезагрузки `/api/me` | перезапрос на `visibilitychange` (только фронт) или в видео заново открыть Mini App |
| Д10 | Бот ничего не шлёт о запросах | родитель не узнает о запросе вне приложения | для видео не нужно; опционально — сообщение родителям при `createRequest` (риск: деплой, токен) |
| Д11 | Данные демо-семьи в prod | после прогонов `allocation` может быть уже испорчена | перед записью сбросить семью (seed-скрипт T19 только для эмулятора — для prod нужен ручной сброс или `--prod`) |
| Д12 | Где подросток увидит изменение | «Мои договорённости» ведут на главную (`onOpenAgreements={goHome}`) | видно в строке главной «Развлечения X · резерв Y» и в бюджете недели — для видео достаточно |

### Что меняется в коде

- **functions:** `PATCH` договорённости подростка (Д2), `teenTelegramId` в запросе (Д4), рост бюджета при одобрении (Д3). Деплой — владелец проекта, сегодня.
- **v2/web:** экраны 1–4 родителя по макету на текущих данных, токены темы Telegram, заглушки уровня, число квестов из данных семьи.
- **Подросток:** без изменений.

### D11. Запрос = «+N ₽ к недельному бюджету» (решение владельца, 2026-11-01)

Закрывает Н1 и Д3. Категория — в тексте объяснения. Вход в запрос — с главной подростка (плюс остаётся последним шагом цепочки квеста 2). Тот же запрос — для срочной покупки, когда не хватает резерва (D4, после T22).

Что это задевает (сторона подростка меняется, но сценарий тот же):

| Где | Сейчас | Нужно |
|-----|--------|-------|
| `validateRuleChange` (`domain.ts` + копия во фронте + тесты) | `proposed ≤ 1 500` — запрос «1 600» отклонится | проверять прибавку `N > 0` (и разумный потолок), а не абсолютную сумму развлечений |
| `RequestDoc` | `category: "entertainment"`, `currentAmount` = развлечения | `kind: "weekly_budget"`, `currentAmount` = текущий недельный бюджет подростка, `proposedAmount` = бюджет + N, `teenTelegramId`; старые запросы читать как раньше |
| `decideRequest` (approve) | развлечения = `proposedAmount` | `teenWeeklyBudgets[teen] = proposedAmount`; прибавку положить **в резерв** (сумма категорий = бюджету, подросток потом переложит сам) |
| `NewConditions` | «Сколько на развлечения», слайдер 100–800 | «Сколько добавить в неделю», слайдер +50…+500, подсказка «напиши, на что» |
| `TeenHome` | строка запроса «Развлечения: X → Y»; входа в форму нет | «Бюджет недели: X → Y ₽» + кнопка «Попросить больше» |
| `RequestStatusTeen`, `ParentRequest`, экран 2 родителя | тексты про развлечения | тексты про недельный бюджет; «Своя сумма» = одобрить с другой N |

Квест 1 после одобрения пересчитывается под новый бюджет сам (`selfWeeklyBudget`). DoD п. 3 («запрос на изменение правил с суммой и объяснением») формально выполняется. Варианты: (а) оставить как часть цепочки квеста 2 для демо; (б) сделать запрос «+N ₽ к недельному бюджету» с целевой категорией и дать вход в него с главной подростка — тогда он же подходит для срочной покупки (D4).

## 12. Запрос подростка по категории (T28, 2026-11-01)

**Решение владельца:** подросток, меняя сумму **существующей** категории, не меняет её сам — уходит запрос родителю (`category_change`) для любого источника денег (резерв или бюджет). Родитель решает на экране «Запросы»: одобрить, своя сумма, отклонить, «расскажи ещё». Одобрение применяет `changeCategory` к **текущей** договорённости (лимиты могли поменяться после запроса). Закрывает Д12: подросток видит свои категории на экране «Мои договорённости».

**Открыто:** применять ли перекладку из резерва сразу, без родителя. Решается вместе с задачей о новых категориях (D3, Н4) одним правилом для новых и существующих категорий. Поле `fundingSource` в запросе оставляет место: «резерв → применить сразу» добавится одной веткой в `createRequest`.
